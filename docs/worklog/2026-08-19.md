# 2026-08-19 — closing out Phase 0

## Where this started

An audit of the repo against the docs. It turned up two kinds of gap: things the backlog knew were
missing, and things the docs no longer described accurately.

The most useful finding was not on any list. **Nothing has been merged.** `main` is still at the
scaffold commit; thirteen commits of real work sit on `feat/availability-and-queries`, and PR #2
has quietly grown to carry the SMS gateway, the payment webhook, the sandbox gateway, the entire
Angular client and a docs rewrite — none of which its title mentions. Merging is being handled
separately; this session worked forward from that branch instead.

## What was built

Five things, in the order they blocked a launch.

**Rate limiting.** The per-code attempt cap bounded guesses against a code that had already been
sent; nothing bounded how many got sent. Two layers now, and they stop different attacks: per
phone number in the service, because the number is what costs money and rotating IPs must not buy
a sixth message to the same handset; per caller at the HTTP edge, because one IP walking a list of
numbers is a different problem. The webhook is in the second bucket too — it is anonymous and pays
for an HMAC over the body before it can reject anything.

**Payment order expiry.** `Cancelled` existed as a status nothing ever set. A hosted service now
sweeps. The decision worth recording is what happens when a payment lands *after* we gave up:
it still credits. Expiry is our bookkeeping and says nothing about whether money moved; refusing
would take the money and hand back nothing.

**Payout failure handling.** The debit is posted when a cash-out is requested, so the credits
cannot be double-spent in flight — but nothing handled the transfer being rejected, and the host's
credits were stranded in a movement that would never land. A rejected payout now posts a
compensating `Refund`. Not an erasure: the failed attempt stays in the history, and the pair reads
as "money left, money came back".

**Disputes.** `Dispute` was a table and nothing else. Raising is limited to the two parties and
only once a session has started. Upholding posts a fresh `AdminAdjustment` rather than editing the
original settlement, and asks the operator two things explicitly — how much, and who pays.

**Refresh tokens.** Access tokens lasted twelve hours with no way to revoke one, which was never
going to be fixable on the access token itself: a JWT carries no server-side state. So the session
moved onto something we store. An hour for the access token, a month for a rotating refresh token,
and signing out now ends something.

Then the two console screens those endpoints needed, and a geo-search integration suite.

## Decisions

**Charging a dispute refund to the host can fail, and should.** If they have already cashed out,
their earning balance cannot cover the clawback — and it cannot go negative without breaking the
invariant everything else rests on. The operator is then choosing between charging the platform
and waiting for the host to earn again. That is a real decision and resolving it silently would be
worse than the error.

**Replaying a spent refresh token revokes the whole family.** Either it leaked or a client is
retrying a refresh whose response never arrived, and there is no way to tell from the server. The
honest client signs in again; the thief gets nothing. The asymmetry favours the safe reading.

**A dispute refund is capped at what the session collected.** Without a ceiling the console is an
unaudited money printer, and the cap is the only thing tying an adjustment to the thing it is
compensating.

**Integration tests skip rather than fail without a database.** A developer with no Postgres
running should not see a red suite for code they did not touch. CI sets the variable in the job
that already has a PostGIS container, so the coverage is not optional where it counts.

## Traps hit

**Three existing auth tests broke on the resend cooldown**, having requested a second code with
the clock frozen. They now advance past it — they describe a user who waited, and the user who
does not now has a test of their own. Worth noting the shape: a rate limit added to a service is a
behaviour change for every test that used it impatiently.

**The dispute test helper reused one idempotency key.** The second call got handed the first
caller's booking, and the failure surfaced as a `ForbiddenException` from a completely different
service. Then the same helper broke again because the first session had advanced the clock an hour
and the second booking was "in the past". Both are the harness being realistic rather than wrong.

**The Angular refresh has to be shared.** A burst of requests all hitting an expired token would
each start a refresh, and since every rotation invalidates the last, the losers would look exactly
like a replay — the client would log itself out by trying too hard.
