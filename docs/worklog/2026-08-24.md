## Running it without Docker

Docker is not running on this machine and is not wanted here. It turns out it was never needed:
`appsettings.Development.json` points at port 54321, which is a native Postgres 12 installed
alongside another application, and it already had a `parknest` database with PostGIS 3.4 in it.

Five migrations had never been applied — the database was still at `AddPaymentOrders`. Applying
them stopped at `btree_gist`, which needs a superuser, and the `parknest` role is not one. The
instance's `pg_hba.conf` trusts `::1/128`, so the extension went in as `postgres` over IPv6
loopback. That includes `AddKycAndBookingOverlapGuard`, which the 2026-08-21 log records as
generated-and-read-but-never-run: the booking-overlap exclusion constraint is now real outside CI.

## FCM in the app

The API has registered device tokens and pushed to them since 2026-08-21; the app never handed one
over. It does now, and the shape of it is governed by one constraint: **the repository must still
build and run with no Firebase project**, because there isn't one and creating it is not a coding
task.

So the Google Services Gradle plugin is applied only when `google-services.json` exists, and
`Firebase.initializeApp` throwing is caught and leaves push disabled. Everything else is unaffected
— the durable notification is written server-side, listed in the app, and counted on the bell,
which was always the design. Drop the file in and push works on the next build.

Three decisions inside `PushService` worth keeping:

**The permission is asked for after sign-in, not at launch.** A notifications prompt on first
open, before the user has an account or a booking, is a prompt about nothing, and the answer to it
is usually no — permanently.

**Registration repeats on every start.** The platform rotates a registration token whenever it
likes: after a reinstall, a restore, a long silence. A token registered once is a handset that
quietly stops receiving anything, and nothing about that failure is visible from either end.

**Unregistering hangs off sign-out, not off the session listener.** The endpoint is authorised, so
it has to run while the tokens are still valid — by the time a session listener sees the change,
`Session.clear` has already happened. `Api.beforeSignOut` is a callback rather than a direct
dependency because `PushService` already depends on `Api`, and the cycle is not worth having.

The foreground case needed its own answer: a push that arrives while the app is open draws nothing
by itself, and waiting up to a minute for the existing poll would make the badge feel broken on the
one occasion the user is watching it. The push is the hint; the count still comes from the server,
which is the only thing that knows what has been read on another device.

## Phase 2: caching geo-search

A decorator over the PostGIS query, and left out of the DI chain entirely when caching is off
rather than registered and told to stand aside — a disabled cache still sitting in the call path is
a class nothing exercises until the day somebody switches it on in production.

**Off by default, and that is not a stopgap.** One indexed PostGIS query is inside its latency
budget on a single city. A cache earns its place when the same few thousand origins are asked for
repeatedly across several instances, which is a multi-city problem. Requiring Redis to run the app
would put that cost in every developer's setup instructions years early. `Memory` is a real option
rather than a test double: on a single instance there is no second instance for a shared cache to
share with, so it gives the whole benefit and costs nothing.

Two things about it were not obvious going in.

**The origin has to be rounded or the cache never hits.** A phone's GPS moves several metres
between two taps and every reading is a distinct key. Rounding to four decimal places — about
eleven metres — collapses neighbouring requests onto one entry. The cost is real and worth naming:
the distances in a cached result are measured from the rounded point, not the caller's exact one.
Bounded by the cell, invisible next to a figure displayed as "120 m away", and the reason the
precision is configuration rather than a constant.

**Invalidation cannot be targeted, and pretending otherwise would be worse.** A listing that
appears, moves or is withdrawn changes the answer for every origin within its radius — an unbounded
set of keys built from coordinates nobody recorded. So invalidation moves a generation counter that
the keys are built from: one write makes all of them unreachable, and the orphans expire on their
own. The counter is a timestamp rather than an increment, which means it needs no atomic
read-modify-write; two invalidations racing both write a value nothing has issued keys under yet,
so either winning is correct.

Every field of the query is in the key. A filter left out is the classic way a cache becomes a
correctness bug — a scooter search served the car results — and there is a test per filter.

Redis failures are swallowed at every operation. A cache is an optimisation, and an optimisation
that can take the search endpoint down when Redis restarts is a liability: a failed read is a miss,
a failed write is forgotten, and the request goes to PostGIS exactly as it would with caching off.

## Phase 2: band management with an audit trail

Price bands change without a deploy. That is the point of them, and it also means they change
without a commit — a band that moved has nothing in git to show for it, and a renter disputing what
they were charged is asking about a row that has since been overwritten.

`pricing_band_changes` is the answer: append-only, one row per edit, both sides of it, who made it
and why. The band row stays current-state; history is a separate table rather than versioned band
rows because every read path wants the band in force *now*, and making them all filter on a
validity window would tax the hot path to serve the rare question.

Details that mattered:

**City and zone are copied onto the audit row, not joined.** "What did Indiranagar look like in
March" must not depend on that band still existing, or still carrying the same city and zone.

**Deactivation is its own kind, not an update.** Switching a band off stops every listing in that
zone from publishing or repricing, which is the most disruptive thing the screen can do, and it
should be findable without reading each row's before-and-after.

**An upsert that changed nothing still writes a row.** That somebody opened a band and saved it
untouched is worth knowing when tracing how a price got where it is, and suppressing no-op rows
leaves gaps in the history that read as inactivity.

**A blank zone is normalised to null.** `""` and `null` are two different rows to the unique index
and the same thing to an operator who cleared the field — the difference is a shadow band, and
whichever one `GetBandAsync` happened to pick would become that city's price ceiling.

The controller lost its logic to a service on the way. It was writing to the DbSet directly, and
an audit row written by the controller is one that the next caller of the same operation forgets.

The reason field is optional. Requiring it produces "update" and nothing else; asking for it on
every edit is worth doing because the numbers are already in the table and the reason is the only
part a later reader cannot reconstruct.
