# 2026-09-21 — counting what the site does

The site is hosted now and nobody could say whether anyone was using it. Render's dashboard counts
requests, which answers "is the process up" and not "did anybody open this". The existing
Prometheus counters are better, but they need Grafana pointed at the container, they only count
what the business does, and the one thing worth knowing first — how many people arrived and how
many of them got as far as paying — was not in there at all.

So: a hit counter, with the rest of the funnel attached.

## What it records

One table, `analytics_events`, one row per thing that happened. The vocabulary is a closed set in
`AnalyticsEventNames`, and it is split down the middle:

- What a **browser** may report: `site.visit`, `page.view`, `search.run`.
- What only the **API** records: `auth.code_requested`, `auth.signed_in`, `auth.signed_up`,
  `booking.created`, `booking.cancelled`, `booking.completed`, `payment.started`,
  `payment.succeeded`, `payment.failed`, `dispute.raised`.

That split is the whole security model of the ingest endpoint. It has to be anonymous — the visit
worth counting happens before anyone signs in — so a client that could name its own events could
claim a thousand payments and make the funnel worthless. A name not on the first list is dropped,
silently, with a 204: an error distinguishing a known name from an unknown one is a probe for the
names that count.

The bookings and disputes come off the existing event bus, as a third subscriber alongside
notifications and the Prometheus counters. Nothing new had to be published, and switching analytics
off cannot touch the messages a renter actually receives.

Payments are the exception and are instrumented in the payment service itself, because a payment
*attempt* is not a fact the system publishes — nothing downstream cares that somebody opened a
checkout page. `payment.started` goes in when the order is created; `payment.succeeded` goes in
inside `PaymentSettlement`, which is the one place all three routes to a gateway's verdict converge
and the one place an order can pass through once. Counting it at the webhook instead would
double-count every gateway that retries.

## What it does not record

No IP address, no email, no name. A visitor is a random id their own browser mints into local
storage, and a visit is a second random id in session storage that dies with the tab. Someone who
clears their storage becomes a new visitor, which is the honest meaning of that number anyway.

The path is the route with the query string cut off and ids folded into `:id` — `/wallet?orderId=…`
is how a payment returns, and a live order id sitting in a table read for counting is exactly the
kind of leak nobody goes looking for. A referrer is kept as an origin, never a path.

`auth.code_requested` records the channel and not the destination. A row per address that ever
asked for a code would make this a mailing list, which is the one thing it must never become.

## The recorder never throws

`IAnalyticsRecorder.RecordAsync` catches everything and logs a warning. It is called from the
middle of a checkout and from the middle of a booking; a counter that could fail a payment would be
worth less than no counter. A row missing from here costs a number on a dashboard.

It shares the request's `DbContext` and saves through it, the way the notification handlers do, so
every call site records *after* its own save — recording first would commit whatever the caller
still had staged.

## Who can read it

`/analytics` in the console, and `GET /api/admin/analytics/summary` behind it. Two checks, because
they answer different questions:

- the **admin role**, which is what the rest of the operations screens use;
- `Analytics:Viewers`, an email allow-list on top of it. Empty means any admin, which is right for
  a one-person platform. Naming an address is what keeps the revenue figures with the owner after a
  second operator is given the admin role to clear the identity-check queue.

The check lives in `AnalyticsQueries` rather than on the controller, so it holds for anything that
ever reads these figures.

While in there: `Auth:AdminEmails` was only consulted when an account was **created**. Adding your
own address did nothing if you had ever signed in before — which is precisely when somebody adds
it. It is now read on every sign-in and promotes an existing account. One direction only: removing
an address does not demote, because the role is also settable by hand and a config change must not
quietly undo that.

## Keeping it small

This is the only table that grows with traffic rather than with business, and the free Postgres
tier is half a gigabyte. `Analytics:RetentionDays` defaults to a year and a daily sweep deletes
what is past it, in batches of a thousand through the ordinary EF API — the application layer
stays provider-agnostic, and a year of hits removed in one statement would hold a transaction open
over a table the site is still writing to.

`Analytics:Enabled=false` stops every recorder without a deploy, for the day the tier runs short.

## The dashboard

The window is aggregated in memory after one indexed read — at a pilot's volume that is cheaper
than a query per figure, and `MaxWindowDays` is what bounds it. The lifetime totals stay in SQL,
since those span the whole table. When the in-memory pass stops fitting, `GetSummaryAsync` is the
one method to push down into SQL and nothing it returns needs to change.

One chart, one series, one axis, with a control to choose which measure is plotted — two measures
of different scale get two views, never two y-axes. Quiet days are present as zero rather than
absent, because a gap in a chart reads as missing data and not as a quiet day. A table view carries
the same numbers for anything that cannot read a picture.
