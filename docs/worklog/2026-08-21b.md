# 2026-08-21 (second session) — finishing Phase 0 and Phase 1

## Where this started

A crawl of the repo against the phase lists, rather than against the backlog, which turned out to
be describing a system slightly better than the one in the tree. Two of the gaps it found were not
on any list, and one of them was the most consequential thing in the audit.

**KYC had no write path at all.** `RequestCashOutAsync` refuses any host who is not `Verified`, and
nothing in `Application` or `Api` ever set that field. So the check was correct, the flow behind it
did not exist, and a host could earn credits forever without being able to convert one — fixable
only by an `UPDATE` against the users table by hand. A headline feature that silently could not
work for anybody.

**The trust score gated nothing.** It moved on ratings and on violations, and no code read it. The
backlog said it gated cash-out. It did not.

## What was built

**KYC, end to end.** A host submits their name as printed, a document type and number, a
photograph, and optionally the account payouts should reach. An operator reviews it in the console
and approves or refuses with a reason. Approving is what opens cash-out.

**Cash-out on the phone.** Hosts could not withdraw from the app at all — earnings simply
accumulated. The wallet now shows them, and either offers cash-out or says which check is in the
way and links to it.

**The trust score bites.** Below a configurable floor, cash-out is refused.

**Dispute evidence.** Attachments were a URL field. Both parties now upload photographs from the
app while the dispute is undecided, and the reviewer sees them next to the decision, along with
both parties' reputations.

**Listing photos in both clients.** Stored and served since Phase 0, reachable from neither.

**Double-booking, settled by the database.** An exclusion constraint over `(space, [start, end))`
for live bookings.

**The hold and the booking in one transaction.**

**Alertmanager**, with a local sink as the default receiver.

## Decisions

**The document number is not stored.** Four characters, and an HMAC of the whole thing keyed with a
configured pepper. The four are what a human matches against the photograph; the hash answers "has
this document arrived under another account" and answers nothing else. An unkeyed digest would have
been worse than useless — a PAN is ten characters of known structure, so a plain SHA-256 of one is
a lookup table away from the number itself. The pepper is a hard startup failure outside
Development for exactly that reason.

**Verification is a human decision.** An automated document check needs a provider we do not have,
and the cost of guessing runs both ways: approve wrongly and the platform pays real money to a
fabricated identity; refuse wrongly and a real host's earnings are stranded with no explanation.
The queue is slower and honest about being slow. What the reviewer is given instead is the two
signals a single row cannot show — how often this account has been refused, and how many other
accounts have sent this document.

**A submission is a row per attempt, not a field on the user.** A rejection has to survive the
resubmission that follows it. "This account has been refused three times" is exactly what the next
reviewer needs, and a mutable record would have erased it.

**The trust score gates cash-out and nothing else.** Money leaving the platform is the movement
that cannot be undone cheaply, so it is the right place. The floor is 40 against a scale where a
rating moves the score by at most six and a violation by ten: reaching it takes a sustained
pattern, not one annoyed renter. That asymmetry is the whole design — the score protects the
platform from a bad actor without handing any single counterparty a way to freeze someone's income.

**Whoever owns the transaction owns the retry.** Making the hold and the booking atomic broke the
ledger's own retry loop, and not in an obvious way: Postgres marks a transaction aborted after a
failed statement, so retrying inside one fails every subsequent command, including the query the
recovery path uses to check whether it had actually won. The ledger now defers when a transaction
is already open, and the booking service repeats the whole unit instead.

**A constraint the database enforces, with the application check kept in front of it.** The check
gives a good message; two requests can still pass it in the same instant. The exclusion constraint
is the guarantee, and `SaveChangesAsync` translates its violation back into the same sentence the
check would have produced — otherwise the loser of that race gets a 500 about a constraint name for
something that is simply "somebody was faster".

**Alerts route to a local sink by default.** A Slack URL nobody has filled in is a delivery path
that fails silently at the far end, which is worse than no path. The sink prints what it receives,
so "did the alert actually leave Alertmanager" is answerable.

## Left dangling

Two things, both the same shape — an account to open, not code to write:

- **Razorpay against the live API**, and the payout leg with it. The escrow arrangement does not
  exist, so an operator still records each transfer by hand.
- **FCM in the app.** The API registers device tokens and pushes to them; the Flutter side needs a
  Firebase project and `google-services.json`.

And one that is a decision rather than a task: **who is on call.** Alertmanager routes; the rota
is not something a configuration file can settle.

## Verification

266 unit tests, `flutter analyze` clean with 33 tests, the Angular console builds. The new
migration was not applied to a live database — Docker is not running on this machine — so its SQL
was generated and read instead. CI's `migrations-apply` job runs it against a real PostGIS, which
is also the only place the exclusion constraint can be exercised at all.
