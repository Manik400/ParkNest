# 2026-08-21 — closing the gap between the API and the phone

## Where this started

Phase 1's list had three things left on it, and they were all the same shape: work the backend had
finished and nothing else could reach. Tier 2 check-in accepted a scan no app could produce.
Ratings were an endpoint nobody was ever prompted to call. Notifications were rows a renter had no
screen to read. Alongside them, metrics that nothing drew and a socket-only delivery that missed
exactly the case it was built for — a phone that is not connected.

## What was built

**Tier 2 in the app, both ends.** The host draws their space's QR on their own handset and prints
it; the renter scans it to check in. The scan is worth more than a tap only because of what it is
paired with, so the app takes a precise fix — GPS-grade, not the coarse one search uses — and
sends the code and the position together or not at all.

**Ratings.** A finished booking asks the server whether a rating is still owed, rather than
working out "finished, you were party to it, you have not already had your say" a second time on
the handset. Where it is not owed, the screen offers the counterparty's reputation instead: the
star average, and the trust score explained as the different thing it is.

**Notifications.** A list, an unread badge, and a tap that opens the booking it is about. Polled
once a minute — the app holds no socket, and a badge is not a figure anyone acts on to the second.

**FCM push.** Sent from the same place the durable notification is written, immediately after it
commits, carrying the same title and body. Device tokens are per install rather than per account.

**Grafana.** `ops/`: a provisioned Prometheus and Grafana in compose, one dashboard, three alert
rules.

**CI.** A mobile job. The app had grown to five thousand lines with nothing checking it.

## Decisions

**A scan without a location is not a weaker proof — it is the attack.** The tempting fallback,
when the fix times out in a basement, is to send the code alone and let the server decide. But a
code with no position is exactly what a photographed sticker produces, which is the thing the
geofence exists to catch. So a failed fix falls back to the Tier 1 tap, and the check-in is
recorded honestly as the renter's word.

**The QR carries a URI, not the bare token.** `parknest://check-in?token=…`. Two things follow:
the scanner can reject the takeaway menu taped next to the sticker immediately instead of sending
it to the server to be refused, and a generic camera app shows the user something they recognise.

**The host's QR is drawn on the handset.** Fetching it as an image would have been less code and
would have put the token in a URL — and a token in a URL ends up in every cache and access log
between the phone and the server. It is the whole secret behind a Tier 2 check-in.

**A device token identifies an install, not an account.** So registering a token already known
under a different user *moves* it. Someone who signed in on a friend's phone must stop receiving
their bookings there the moment the friend signs back in; two rows would have pushed every message
to both.

**Push may fail; the notification may not.** The push happens after the row commits, inside a
`try` that logs and returns. This runs in an event handler on the far side of a settlement that
has already happened, and the message it carries is sometimes "your account is restricted" — a
Firebase outage costing that would be indefensible. Tokens Firebase reports as dead are pruned on
the spot, because nothing else would ever notice them.

**No Production guard on push.** SMS and payments refuse to boot unconfigured, because a login
that prints its own OTP and a gateway that mints free credits are both catastrophic. Push is not
in that class: with it off, every message is still stored and still socketed. Refusing to start
would take the platform down to protect a convenience.

**FCM v1 by hand, not Google's client libraries.** The whole need is: sign a JWT with the service
account key, exchange it for an access token, cache it, POST. That is a hundred lines against a
dependency tree measured in megabytes. The legacy static-server-key endpoint would have been
simpler still; Google turned it off in 2024.

## Left dangling

- The app registers no device token. It needs a Firebase project and `google-services.json`, which
  is an account to create rather than code to write. The API side is built and tested.
- Nothing routes a firing alert to a person. That needs a destination and an on-call decision.
- The admin console still cannot see a rating or a trust score, which is the next thing a dispute
  reviewer would ask for.
