# 2026-07-30 — Availability enforcement and the read side

Branch `feat/availability-and-queries`, cut from `feat/auth-identity` (PR #1, still open).

## What was done

**Availability is now actually enforced.** `AvailabilityWindow` and `AvailabilityBlackout` had
been modelled, persisted and exposed since the first commit — and never once checked. A space
offered 09:00–17:00 could be booked at 3am. `BookingService` now validates the requested window
against the host's published hours before reserving any credits.

The comparison happens in the space's own time zone. `ParkingSpace.TimeZoneId` (IANA, defaulting
to `Asia/Kolkata`) was added for this, which also closes the multi-city timezone question that was
sitting in the backlog's open list — availability is wall-clock, so without it every host's hours
would have been silently interpreted in the server's zone.

`AvailabilityCalculator` is pure and separately tested: overnight windows (22:00–06:00), bookings
that cross midnight, gaps between two windows on the same day, and adjacent windows that should
merge into one continuous opening. Equal start and end means 24 hours, which is how a 24/7
basement is expressed.

Two smaller rules fell out of the same work: publishing a listing with no availability is now
refused (it would only ever be a dead pin on the map), and a booking cannot start in the past
beyond five minutes of clock-skew tolerance.

**Read endpoints**, because there were almost none and no frontend could have been built:
my bookings, hosting bookings, booking detail with its ledger trail, my listings with active
booking counts, listing detail, and wallet transaction history.

## Decisions

Read queries live in `Application/Queries` rather than on the command services. They do no
business reasoning — authorise, project, return — and keeping them separate stops read-shaped DTOs
leaking into the services that move money.

Empty availability means *never open*, not *always open*. Failing closed is the right default when
the resource is someone's driveway.

## Things worth noting

The query layer is an authorisation surface in its own right, so it has its own tests: a stranger
cannot read a booking they are not party to, a host sees only their own listings, a draft listing
is invisible to everyone but its host, and a new user's ledger is empty rather than someone
else's. A read leak here would expose other people's movements rather than let anyone spend
credits, which is a different failure but not a smaller one.

`dotnet ef migrations remove` needs a live database, which was not running locally, so the
first `AddSpaceTimeZone` attempt (which defaulted the column to an empty string — an invalid time
zone for every existing row) had to be unpicked by hand: delete the two files, `git checkout` the
model snapshot, fix the entity configuration, regenerate.
